Averaging belongs to the application/project sensor logic, which hands the shared core a completed record ([Buffer integration](firmware-base-and-serial-api.md#buffer-and-consumer-integration)); snapshot versus durable handoff, append results and queueing remain open. CESH's `appendReadingToBuffer` is the modeling baseline for the Buffer interface ([append reference](firmware-buffer-api.md#compatibility-and-cesh-evidence)); its `bool` result is not adopted over the proposed interface. The facade performs generic sample checks (finiteness, declared types, required fields, declared bounds) with per-channel outcomes ([sample checks](firmware-base-and-serial-api.md#loop-service-and-records)); result types, all-null acceptance and atomic versus partial publication remain open. The exact API, folder layout and runtime model remain proposed. October 20 user correction: the student starter and the reusable core are colocated in `bardbox-project-template/software/firmware/` (core libraries as `lib/` siblings of `src/` and `include/`); authoritative architecture and contracts stay in `bardbox/docs`, and bardbox keeps no duplicate core under `bardbox/software/`. This supersedes the earlier split-home recommendation (core in bardbox, starter in the template; [FW-MAC-1 record](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6289751206), [FW-CHECKPOINT-1](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6290013749)). [FW-LAYOUT-1](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6290294824) accepts the combined [starting layout](firmware-blueprint.md#2-source-tree); a role-README-only scaffold exists on template branch `codex/firmware-starter-scaffold` (not merged; no code, config or build change). The user's later simplification removed `src/application/` and `src/application/sensors/`: students start in `src/main.cpp`. Accepted [FW-SIMPLE-1](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6290658288) direction: one student hand-off of a completed data point (raw or application-averaged), routed internally by configuration (serial and Wi-Fi by default, Buffer on by default; a serial-only device disables Wi-Fi by configuration with the same hand-off); serial keeps request/opt-in-stream behavior with no unsolicited `DAT`. Accepted [FW-SENSOR-PUBLISH-1](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6291563410) ([acceptance](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6291568725)): the hand-off is `sensor.publish(values...)` with already-acquired values in declared measurement order (no student record builder or global publish); count, type, finiteness and bounds are checked but same-type swaps cannot be detected; exact signature, per-sensor versus full-node grouping and the versioned serial/server mapping are an open gate before code. Student view: three concepts, startup (`begin(options)` once; accepted defaults Serial + Wi-Fi + recording ON, Serial always present; proposed MVP profile offers no recording-off option and Wi-Fi off only as a future serial-only option, never Wi-Fi without Buffer; the existing assessed-omission exception in the Buffer proposal remains; credentials never `begin` flags), the one hand-off and the effective interval. This supersedes the unaccepted two-hand-off draft; the name `publish` is accepted while its exact signature, result types and policies remain proposals; beginners call `begin()` with no arguments (no baud argument or required flags; the existing 115200 serial default governs, configurable in a labelled Serial section of one `include/config.h`; Serial, Network and Buffer sections are read and validated by their own modules, with no settings framework and no default secrets ([simple configuration layout](firmware-base-and-serial-api.md#operational-settings))) ([student contract](firmware-base-and-serial-api.md#proposed-student-contract-draft-for-review)). Measurements belong to sensor instances ([FW-SENSOR-1](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6291273464)): `bardbox.addSensor(name)` returns a typed sensor handle (`BardBoxSensor` recommended; spelling, attachment and lifetime proposed) whose `addMeasurement` declares its channels; the one `BardBoxInterface` device still owns transports, the Buffer, the UID and `publish`; sensors get no queues, transports or identities; hardware initialization stays explicit; the same name may appear under separate sensors, and wire naming and per-sensor grouping remain open. [FW-SENSOR-2](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6291413717): a sensor is created and registered once through the interface with an explicit runtime name (no `addSensor(existingObject)`, hidden global registration or automatic hardware init; factory versus constructor syntax proposed); optional types use constants such as `MeasurementType::Integer`/`MeasurementType::Boolean` (spelling proposed); an Integer-declared channel never silently truncates fractional input, so the application rounds explicitly or the channel is invalid. Measurements are registered with `addMeasurement(name, unit, optionalType)` ([FW-MEASUREMENT-1](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6291173701)): omitted type means FLOAT, Integer for exact counts, Boolean distinct, no double requirement; integer values passed to FLOAT are a documented conversion that may lose precision for large integers; widths and representability policy remain design. Application averaging reads the active reporting interval through the existing proposed `getSetting(name)` ([reporting interval](firmware-base-and-serial-api.md#operational-settings), [FW-INTERVAL-1](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6290622655)); its key, units representation and any live-change or partial-window policy remain proposed, and there is no student service call: `begin()` starts internal BardBox service that continues during student `delay()` ([FW-SERVICE-1](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6291462264), [acceptance](https://github.com/bardphysicslab/bardbox/issues/31#issuecomment-6291470459); the single service task, bounded admission slots and the first begin/read/publish/delay acceptance test are a [proposed design](firmware-base-and-serial-api.md#internal-service-design-proposed), not implemented). The beginner facade's accepted name is `BardBoxInterface` (replacing the `BardBoxDevice` candidate); other library names, packaging and the [student contract draft](firmware-base-and-serial-api.md#proposed-student-contract-draft-for-review) (API, all-null, partial publication, durable handoff) remain proposed. Retained local template PCB work stays preserved and does not block independent shared documentation. No implementation or adoption |
